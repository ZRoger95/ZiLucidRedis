# 源码注释约束设计

日期：2026-11-21
状态：已实现
范围：清理 `src/` 手写源码中的解释性注释，并禁止后续新增普通源码注释；覆盖 TS、TSX、CSS，不覆盖生成数据。

## 意图：为什么做

AI Agent 会把注释当作代码上下文；过时或带有实现借口的注释可能误导后续修改。项目希望验证一种更精简的代码库约束方式：用代码结构、类型、测试和 lint 表达可执行事实，把需求与设计理由放在文档中，而不是散落在源码注释里。

## 目标与边界

- 删除 `src/` 手写 TS、TSX、CSS 中的普通解释性注释和 JSDoc。
- 在 `AGENTS.md` 记录此约束和动机：Agent 不新增普通代码注释；需求、原因、约束写入对应文档。
- 在 `npm run lint` 中加入注释门禁，阻止 `src/` 手写源码新增普通注释。
- 允许 ESLint、TypeScript 等工具必须识别的指令注释；门禁须对这些指令设明确豁免。
- 保留 `src/data/` 等生成数据中的 Redis 配置注释，它们是产品数据，不是源码注释。
- 不改变运行时行为，不移除 UI 文案、Redis 配置注释或字符串中的注释示例。

## 方案

已选：**文档约束 + 自动检查**。ESLint 核心规则不能精确禁止所有源码注释并保留工具指令；实现一条轻量本地 ESLint 规则检查 TS/TSX，并将 CSS 纳入同一 lint 门禁（可用本地检查器处理 ESLint 不解析的 CSS）。不新增依赖。工具指令白名单以实际需要为准，避免把普通说明注释伪装成豁免。

放弃的方案：

- **只写入 `AGENTS.md`**：依赖 Agent 遵守软规则，不能在 lint 中稳定发现回归。
- **删除所有注释语法**：会破坏 ESLint 禁用/配置指令、TypeScript 引用指令等工具行为。
- **只清理 TS/TSX**：CSS 仍可继续积累普通源码注释，与 `src/` 全覆盖目标不符。

## 验收标准

- `src/` 现存普通解释性注释已清理；需要保留的工具指令有明确、最小的豁免。
- 在 `AGENTS.md` 中可找到“不要新增普通源码注释”的约束和文档归属说明。
- `npm run lint` 能拒绝 TS、TSX、CSS 中的普通注释，同时接受获准的工具指令。
- 应用行为不变，生成数据中的注释不变。
